# 问题：当前保留成果

更新时间：2026-09-19
状态：试用

## 这次讨论留下了什么

这次讨论的价值，不在于把“问题”定义成一个漂亮的哲学概念，而在于确认了一件工程上的事实：

**“问题”本身应该成为研究系统中的独立对象，而不能只是 Prompt 里的几句话。**

当前至少可以保留以下三层区分：

### 1. 问题不是答案的容器

一个问题不是为了把一个已经知道的任务换一种说法。

真正有价值的问题，应当明确：
- 我们究竟在追问什么；
- 当前缺少什么认识；
- 什么事实或判断可以使这个缺口发生变化；
- 什么结果能够证明这个问题已经得到回答。

因此，问题定义本身就是研究动作的一部分。

### 2. 问题图不是“知识分类图”

问题图的作用不是把所有知识点装进一个分类体系。

它更接近一个**问题拆解与编排层**：

研究意图 → 问题 → 子问题 → 研究动作 → 证据/判断 → 交付

所以，问题图首先服务于“下一步研究什么、为什么研究、这些研究之间有什么依赖”，而不是展示一个领域有多完整。

### 3. “问题”与后续研究产物需要分离

目前应明确区分：

- 问题：要解决的认知缺口；
- 问题链：多个问题之间的依赖和推进关系；
- 研究动作：为回答问题而执行的具体操作；
- 证据：支持或削弱判断的材料；
- 判断：基于证据形成的阶段性认识；
- 交付：面向使用者组织后的结果。

这一区分比继续增加术语更重要。后续如果发现这些边界在真实项目中不能稳定工作，再修改。

## 当前暂不固化的部分

下面这些内容目前只作为研究方向，不视为正式规范：

- “问题”的完整本体；
- 问题对象的统一字段；
- 问题之间的全部关系类型；
- 是否需要独立的形式化语法；
- 是否最终采用图数据库、知识图谱或其他实现；
- 是否把这一套结构直接做成 Agent 的执行协议。

理由很简单：这些东西还没有经过足够的真实任务验证。

## 与 AI 投研系统的关系

在当前 AI 投研体系中，“问题”这一层位于研究意图与具体研究执行之间。

因此，**问题图模块可以暂时理解为整个系统的“问题拆解与编排层”**。

它的价值不是替 Agent 直接完成研究，而是给 Agent 一个可执行、可追踪、可回溯的研究入口。

后续需要用真实研究项目继续验证：
1. 一个问题能否被稳定拆成可执行的子问题；
2. 子问题是否能够对应明确的研究动作；
3. 研究结果能否回填到问题；
4. 问题结构变化时，交付物是否能够同步变化。

## 这份资产的使用边界

这不是最终的“问题本体规范”，也不是给 Agent 直接执行的 Skill。

它目前只记录已经形成的概念边界，作为后续工程化时的基线。

真正稳定的定义，应当来自真实项目中的反复使用和修订，而不是一次理论讨论。
